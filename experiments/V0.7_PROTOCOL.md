# V0.7 Experimental Protocol — External Semantic Validation Pilot

## Research question

Can BIZPROOF formally validate a business-semantic rule taken from independently developed
software after a small, explicit, reviewer-visible adaptation into the currently supported
scalar verification language?

## Source systems

The pilot uses the exact commits already locked by V0.6.2:

- OpenFisca-France:
  `ebcb7782d17058495c6ca33c278e373e167b641b`
- Django-Oscar:
  `5699d78449954f047d6d715fd2b6c5d19594e0f3`

## Selected rules

Four rules are included:

1. OpenFisca apprenticeship-tax liability.
2. OpenFisca housing tax after relief.
3. Django-Oscar CountCondition partial-satisfaction boundary.
4. Django-Oscar CountCondition satisfaction threshold.

The pilot deliberately excludes technical methods such as `__str__`, `__repr__`, generic
getters, and infrastructure-only methods even when V0.6.2 found exact evidence for them.

## Adapter policy

An adapter must:

- be scalar and deterministic;
- contain only semantics already visible in the locked external source;
- record every abstraction operation;
- record any representation change;
- have a source path, symbol, commit, and external evidence file;
- remain small enough to inspect directly.

Two adaptation scopes are used:

### RETURN_EXPRESSION

The external return semantics are translated directly to supported scalar Python.

### POST_AGGREGATION_THRESHOLD

An external object/database aggregation is treated as an explicit scalar input. BIZPROOF
verifies only the threshold rule after aggregation. No claim is made about the correctness
of the original aggregation loop or database/object machinery.

## Representation policy

The housing-tax rule uses non-negative integer monetary units instead of external floating
values. The claim is restricted to the order-preserving clamped subtraction
`max(tax - relief, 0)`.

## Evidence independence

Contracts are grounded in external source behavior together with external tests/YAML
specifications. The external implementation and evidence file are provenance-checked against
the V0.6 lock before the experiment runs.

## Primary outcomes

For each correct adapter:

- expected verdict: `PROVED`.

For each deliberately injected mutant:

- expected verdict: `DISPROVED`;
- concrete replay must validate the counterexample.

The mutant experiment is a secondary sensitivity check only. Injected mutants are not
reported as external software defects.

## Claim boundary

V0.7 does not claim end-to-end verification of OpenFisca-France or Django-Oscar.

A successful result means only that the explicit tracked adapter satisfies the explicit
tracked contract over the declared BIZPROOF domain.
