# V0.6 Experimental Protocol — External Business Rule Corpus

## Objective

Measure external validity before adding more synthetic benchmarks.

V0.6 uses independently developed Python systems and records the exact repository commit
used for every run.

## External systems

1. OpenFisca-France — tax and social-benefit legislation as code.
2. Django-Oscar — domain-driven e-commerce.
3. pretix — ticketing, pricing, quotas, orders, and payments.

## Reproducibility

`./run.sh external-acquire` clones each repository and writes the resolved commit SHA to
`benchmarks/v0.6/LOCK.json`.

External repositories are not committed into BIZPROOF. Only provenance, hashes, classifications,
and experiment outputs are committed.

## Audit

Production Python functions under configured business-oriented source roots are inspected.

Business relevance is determined from transparent lexical signals in:

- function names;
- source paths;
- function docstrings.

Every business-relevant candidate is retained and classified:

### DIRECT_CANDIDATE

The function is structurally close to the currently supported BIZPROOF subset.

This does **not** mean it is already proved. A business contract still needs independent
evidence from project tests, documentation, or normative references.

### ADAPTATION_REQUIRED

The function contains object access, calls, comprehensions, assignments, decorators, or other
constructs that can plausibly be represented through an explicit scalar/interface adapter.

Adapters must be documented and measured in the next V0.6 sub-stage.

### UNSUPPORTED

The function contains loops, exception handling, context managers, async/yield behavior, or
other constructs intentionally outside the current verifier semantics.

Unsupported cases remain in the denominator.

## Outputs

Tracked reviewer artifacts:

- `benchmarks/v0.6/LOCK.json`
- `benchmarks/v0.6/results/summary.json`
- `benchmarks/v0.6/results/candidates.jsonl`

The candidate records contain file paths, line ranges, source/function hashes, evidence file
references, classification, and classification reasons. They do not vendor third-party source code.

## Primary metrics

- external repositories checked;
- source files examined;
- functions examined;
- business-relevant functions;
- direct-candidate rate;
- adaptation-required rate;
- unsupported rate;
- candidates with test evidence;
- candidates with documentation evidence.

This stage measures representativeness and verifier applicability. It does not yet claim that
every candidate business rule is semantically verified.


## V0.6.1 evidence-aware triage

The initial V0.6 audit exposed two measurement risks:

1. business relevance could be triggered by source-path keywords alone;
2. evidence linking ignored YAML/YML test specifications and relied too heavily on exact
   function-name matches.

V0.6.1 therefore reports business relevance separately as:

- `STRONG`: business keywords occur in the function name or docstring;
- `CONTEXTUAL`: business relevance comes from the selected business-oriented source path.

It also records the source of each business keyword.

Evidence linking now supports Python, Markdown, RST, TXT, YAML, and YML files and distinguishes:

- `FUNCTION_TEXT`;
- `MODULE_TEXT`;
- `MODULE_PATH`.

These are heuristic provenance links, not semantic equivalence claims.

For `ADAPTATION_REQUIRED`, a triage-only `adaptation_complexity` field (`LOW`, `MEDIUM`,
`HIGH`) is reported from structural reason count and function span. This ranking is used only
to prioritize manual semantic validation; it is not a verifier-support claim.


## V0.6.2 exact evidence provenance

V0.6.2 removes module-level lexical matching from the evidence denominator.

A file is counted as supporting evidence only when one of the following exact relationships
is observed:

- a Python test AST references the exact function symbol;
- a Python test AST references the exact enclosing class symbol;
- a YAML/YML/TXT evidence file contains the exact function identifier;
- a YAML/YML/TXT evidence file contains the exact enclosing class identifier;
- documentation contains the exact function or enclosing-class identifier.

Generic function names such as `formula`, `calculate`, and `apply` are not accepted as
function-level evidence by themselves.

For OpenFisca-style variable classes, the enclosing class is recorded because the business
variable is represented by the class while the executable implementation is commonly a
generic `formula` method. YAML outputs can therefore link exactly to the variable-class name.

Module-name, module-path, partial-token, and generic keyword matches are not counted as
supporting evidence.

For repositories with tests colocated below the source tree, test discovery may scan a broad
configured root, but only files with a test-like filename or a `test/tests/testing` path
component are eligible as test evidence.
